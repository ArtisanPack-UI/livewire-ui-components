# Upgrading from 2.x

Version 3.0 is rebuilt on the ArtisanPack UI design system. DaisyUI is gone, some components and attributes were renamed to match React and Vue, and theming moved to design tokens. Most 2.x tags still render in 3.0 as [deprecated aliases](Components-Deprecated-Aliases), so an app keeps working while you migrate.

The full guide, with every renamed component, every changed attribute and a table for replacing raw DaisyUI classes, is [Upgrading Livewire UI Components 2.x to 3.0](https://docs.artisanpackui.dev/documentation/design-system/upgrade/livewire) in the design-system documentation. This page covers the upgrade command and the Laravel-side changes.

2.x and 3.0 can't be mixed in one app: the new CSS replaces DaisyUI, and the two style the same components differently. Upgrade the whole app at once, on a branch.

## 1. Update the package

Commit your work first, then:

```bash
composer require artisanpack-ui/livewire-ui-components:^3.0
```

## 2. Run the upgrade command

Preview the changes:

```bash
php artisan artisanpack:upgrade-ui --dry-run
```

The dry run prints a diff of every file it would change and writes nothing. Run it without `--dry-run` to apply the changes; it asks before writing.

```bash
php artisan artisanpack:upgrade-ui
```

| Option | Does |
|---|---|
| `paths` | Files or directories to upgrade. Directories are searched for `*.blade.php` files, skipping `vendor` and `node_modules`. Default: `resources/views` |
| `--dry-run` | Shows the changes as a diff without writing |
| `--no-classes` | Leaves raw DaisyUI classes and theme references out of the report |
| `--json` | Prints the report as JSON. It writes without asking, so pair it with `--dry-run` to only report |
| `--force` | Writes without asking. Required when the command can't ask, as in CI |

Views in a package or a module aren't under `resources/views`, so pass them: `php artisan artisanpack:upgrade-ui packages/billing/resources/views`. If a file changes while the command waits for your answer, it writes nothing and asks you to run it again.

### What it rewrites

```blade
{{-- Before --}}
<x-artisanpack-modal wire:model="confirming" title="Delete order" subtitle="This cannot be undone." separator>
    <x-slot:actions>
        <x-artisanpack-button variant="error" icon="o-trash" label="Delete" tooltip="Delete for good" />
    </x-slot:actions>
</x-artisanpack-modal>

{{-- After --}}
<x-artisanpack-dialog wire:model="confirming" title="Delete order" description="This cannot be undone.">
    <x-slot:footer>
        <x-artisanpack-tooltip content="Delete for good"><x-artisanpack-button color="error" leading-icon="o-trash">Delete</x-artisanpack-button></x-artisanpack-tooltip>
    </x-slot:footer>
</x-artisanpack-dialog>
```

- Renamed components, with their closing tags: `modal` to `dialog`, `header` to `page-header`, `choices` to `combobox`, and the rest.
- Renamed attributes and slots, bound or not, in kebab-case or camelCase.
- Flags that became values (`right` to `side="end"`) and per-part class attributes (merged into `:classes`).
- Button `variant`: a color (`variant="primary"`) becomes `color`; a variant (`variant="ghost"`) stays.
- `label` on a self-closing button moves into the slot.
- Tooltip attributes become a `<x-artisanpack-tooltip>` around the element.

### What it reports

Each line of the report has the file, line and column:

| Label | Meaning |
|---|---|
| `manual` | An attribute, slot or component with no automatic replacement. The message says what to do |
| `review` | A change that was made and deserves a look |
| `removed` | An attribute that was deleted because 3.0 has no equivalent |
| `class` | A raw DaisyUI class (`btn`, `card`, `bg-base-200`), theme variable or DaisyUI configuration |

Raw DaisyUI classes are never rewritten, because the right replacement depends on the element. The full guide says what to use for each.

### What it leaves alone

- Tags that other packages register under the same prefix, such as `<x-artisanpack-ec-price>`.
- Blade comments, `@verbatim` blocks and PHP files.
- Attributes built in PHP or passed through `$attributes`. The command flags tags that build their attributes with Blade, so you can check them.

You can run the command again after fixing things by hand: migrated markup has nothing left for it to rewrite.

The rules it applies are in `resources/design-system/upgrade-rules.php`, generated by the design system from its component manifests and a catalog of the 2.x API.

## 3. Replace DaisyUI with the design system

Remove `@plugin "daisyui"` and any `@plugin "daisyui/theme"` block from your CSS, and `daisyui` from `package.json`. Then load the design system, without a bundler or with Vite, as [Installation](Getting-Started-Installation) describes, and add `@apuiThemeScript` to your layout's `<head>`.

## 4. Move your theme to a preset

A 2.x theme from `artisanpack:generate-theme`, or any DaisyUI theme, has nothing to style in 3.0. Generate a preset from the same brand colors:

```bash
php artisan artisanpack:generate-preset acme --primary="#7c3aed"
```

See [Theming](Theming). `artisanpack:generate-theme` still runs, deprecated, and the `theme_output_path`, `glass` and `design_tokens` config keys only configure it. The `artisanpack-glass-tokens` and `artisanpack-design-tokens` publish tags, the `icons.list_item` and `icons.loading` keys, and the `livewire-ui-components:bootcamp` command are gone. The 2.x theme builder page and its route are gone.

The theme now lives in `data-theme` on `<html>` (`light`, `dark` or `high-contrast`), stored under the `apui-theme` localStorage key. The 2.x `mary-theme` key, the theme class on `<html>` and the `theme-changed` event are gone; ThemeToggle reports a change as `value-change`.

## 5. Check the Livewire-side changes

- **Toasts.** `toast()` now takes the title first: `toast( $title, $description, color: … )`. A 2.x call such as `toast( 'success', 'Saved' )` still runs, with the new meaning, and raises a deprecation notice. Add `<x-artisanpack-toaster />` to your layout. See [Toasts](Livewire-Toasts).
- **Icons.** Components draw icons from the design system's registry (`leading-icon="plus"`). Heroicons names such as `o-user` still render through Blade Icons. See [Icons](Icons).
- **Calendar.** `<livewire:artisanpack-calendar>` no longer loads lazily, and custom event views receive the event in `mount()`. See [Calendar](Livewire-Calendar).
- **Tables.** The export toolbar is gone; `WithTableExport` and `TableExporter` remain for exports you trigger. See [Tables](Livewire-Tables).
- **Spotlight.** The package's Spotlight route and your search class work as before; item icons are now registry icon names, not HTML. See [Spotlight](Livewire-Spotlight).
